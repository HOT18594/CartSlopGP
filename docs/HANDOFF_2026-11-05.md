### Nightly schedule (installed on the Pi)

Time zone is now **America/New_York**. NTP is enabled.

- **00:15 local** — `cartslop-night-stop.timer` stops:
  - `cartslop-connect.service`
  - `cartslop-server.service`
- **07:15 local** — `cartslop-night-start.timer` starts both again.
- The Pi stays powered 24/7 and SSH stays available. This is deliberate:
  a Pi 4 has **no RTC wake alarm**, so a true power-off cannot be guaranteed to
  wake itself. Use a smart plug if a real power cut is required.
- Files:
  - `pi_setup/cartslop-night.sh`
  - `pi_setup/cartslop-night-stop.service`
  - `pi_setup/cartslop-night-start.service`
  - `pi_setup/cartslop-night-stop.timer`
  - `pi_setup/cartslop-night-start.timer`
- Pi logs: `/var/log/cartslop-nightly.log` and
  `/boot/firmware/cartslop-nightly.log`.
- Status file: `/boot/firmware/CART_SLOP_SCHEDULE.txt`.
- The stop/start actions were tested manually; both services returned active.
- If the Pi boots during the sleep window, `Persistent=true` runs the missed
  stop timer, so the server does not stay up all night.

### Server capacity estimate (no stress test)

No stress test was run because the Pi has **no heatsink**; idle temperature was
about 53–57 °C. Official Pi 4 specs: quad-core Cortex-A72 at up to 1.8 GHz,
4 GB RAM, Wi-Fi 5 and Gigabit Ethernet. [cite:22245336-1]

The game sends roughly 8–10 KB/s per client. With 8 players per room that is
64–80 KB/s per room before HTTP/tunnel overhead.

- Comfortable: **5–10 rooms** (40–80 players) for a Python relay on this Pi.
- Practical ceiling: roughly **15–25 rooms** (120–200 players) with wired
  Ethernet and a clean network.
- The real bottleneck is usually the home **upload** link, not the Pi CPU.
- For a 10–20 Mbps upload, expect roughly 10–25 rooms of 8 players in theory,
  with real headroom closer to 5–15 rooms.
- Fighting games: the Pi relay is fine for casual low-ping sessions, but it is
  not a competitive fighting-game server. It adds a relay hop and depends on
  home upload/jitter. Wired Ethernet on the Pi is strongly recommended for
  latency-sensitive play.
- Add a heatsink/fan before 24/7 load; the bedroom placement makes cooling and
  noise worth checking.

## Multiplayer architecture (v0.6.2)

Two ways to start a world, no other:

1. **HOST LAN** — the PC is the ENet server. It advertises on UDP 42779;
   nearby clients use FIND LAN ROOMS. No Pi/internet required.
2. **HOST ONLINE** — the PC registers with the Pi and gets a 5-letter room
   code. Joining is code-only; no IP/port/hostname/14-character codes.

- Pi room states: `lobby`, `playing`, `finished`. Joining a started room is
  rejected.
- Host-authoritative car collisions: two-body normal impulse, restitution,
  Coulomb friction, sent as delta-v to both owners.
- Scene readiness handshake: gameplay RPCs only go to peers that loaded the
  scene; host retries scene start every 5 s; no `Node not found: DrivingTest`.
- Race waits up to 8 s for every peer, then broadcasts a synchronized 3 s
  countdown. SceneLoader has a 12 s threaded-load fallback.
- Esc in multiplayer keeps the world running; single player pauses.
- HUD shows `FPS PING n/8` top-right in multiplayer.
- Changelog panel is paged two releases per page.

## Important known issues / next steps

- Friend on macOS should test the **v0.6.2** build. The new
  `_net_apply_car_impulse` RPC means host and client should both run v0.6.2.
- Pi public IP is dynamic. If it changes, update `DEFAULT_RELAY_SERVER` in
  `scripts/net/network.gd` and the Pi update manifest.
- No full server-authoritative physics; the host is authoritative for
  collisions/props/race start, but each peer still simulates its own cart.
- School networks that block outbound UDP cannot relay a race even though the
  console loads.
- Pi has no RTC and no heatsink; see notes above.
- Router DHCP reservation for the Pi is still recommended.
- `git` repo contains only `godot_project/`; `pi_setup/` and `builds/` are
  outside it.
